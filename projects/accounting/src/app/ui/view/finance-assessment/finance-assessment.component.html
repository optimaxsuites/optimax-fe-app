2 · Cross-Module Payment Flow Architecture — Disbursement Consolidation

✓
Payment Runs (formerly "Disburse") is the correct single consolidation point for all outbound payments, regardless of which module originated the payment request. HR payroll, expense reimbursements, staff loans, vendor payments — all flow through here. This matches SAP (AP Payment Runs), NetSuite (Payment Processing), and Xero (Batch Payments).

How it works — the correct flow

1
Source Module raises a payment request
Each module creates an Accounting Event tagged with its source module. The event definition determines the GL accounts.
HR/Payroll → SALARY_PAYMENT Expense → EXPENSE_REIMBURSEMENT Loans → LOAN_DISBURSEMENT Vendor → VENDOR_PAYMENT
2
Accounting Events queue — Review & Approve
Accountant reviews the event. The event definition maps it to the correct Dr/Cr accounts. Clicking Post to Ledger creates the journal entry. Event status moves to APPROVED.
3
Approved payment events surface in Payment Runs
All APPROVED outflow events appear in the Payment Runs tray — salary runs, expense reimbursements, loan disbursements, and vendor payments in one unified list.
4
CBN Maker-Checker (amounts above ₦500k)
Payments above threshold require a second authoriser. The Maker cannot approve their own payment.
5
Select payment method & disburse
Once authorised, select a payment channel (Paystack, Bank Transfer, Sterling, Cash). A Ledger Entry is automatically posted to close the payable account.

4 · Component-by-Component UI Analysis

📥
Tab 1: "Accounting Transactions" → AccountingQueueComponent
File: accounting-queue.component.html
  • Name mismatch: This is an event review queue, not a transaction register. Rename to "Accounting Events".
  • Dual status codes: Both UNPROCESSED and UNREVIEWED map to "PENDING APPROVAL" — backend inconsistency.
  • Approve disabled silently: No tooltip when matchedMapping is falsy — users don't know why they can't approve.
  • "Delete/Reject" same button: Reject returns to submitter; Delete removes it. These must be separate buttons.
  • "Fiduciary Control" modal: Should be "Confirm Ledger Posting" — "Fiduciary Control" is governance language, not a UI label.
  • ₦ hardcoded: ₦{{'{{'}} ev.amount | number:'1.2-2' {{'}}'}} — blocks multi-currency.
  • No bulk approve: Enterprise queues need ability to bulk-approve low-risk events.
🌳
Tab 2: "Chart of Accounts" → ChartOfAccountsComponent
File: chart-of-accounts.component.html
  • "Deleted Logs" button: Accounts must never be deleted if they have transactions. Use "Archived Accounts" / Deactivate pattern.
  • "Run Report" has no handler: Dead button in production.
  • No Active/Inactive toggle: Can't deactivate without deleting.
  • Missing COST_OF_SALES type: Without this, P&L cannot show Gross Profit — required for IFRS.
📖
Tab 3: "Journal Entries" → BookKeepingComponent (h1: "Financial Journals")
File: book-keeping.component.html
  • Three names for one screen: Component = BookKeeping, Tab = Journal Entries, h1 = Financial Journals. Must unify to "Journal Entries".
  • No journal entry reversal action: REVERSED is a filter option but there's no Reverse button on posted entries.
  • No recurring journal entry: Standard ERP feature for monthly depreciation, rent, etc.
  • No attachment support: Journal entries should support document attachments (scans, receipts).
📤
Tab 7: "Disburse" → DisbursementFlowComponent
File: disbursement-flow.component.html
  • "Disburse" is a verb, not a module name. Rename to "Payment Runs".
  • Only shows HR loans/advances. Should consolidate ALL outbound payment events — payroll, expenses, loans, vendor bills.
  • No payment scheduling: Standard payment runs allow future-dated payments.
  • No multi-level approval: CBN requires Maker-Checker for amounts above ₦500k.
  • Only Paystack as channel: Must support bank transfer, RTGS, cheque, cash.
⚙️
Tab 6: "Settings" → BankConnectionSettingsComponent
File: bank-connection-settings.component.html
  • Critical naming error: Top-level "Settings" tab only controls bank API keys — deeply misleading. Should be a sub-section of Banking.
  • Module-wide Accounting Settings entirely absent: Fiscal year start, base currency, VAT reg number, rounding rules, approval thresholds — not configurable anywhere.
  • API keys visible in settings: apiKey and secretKey fields must be masked after creation.

8 · Architecture & Backend Concerns

🚨
Critical Risk: Client-Side Accounting Pipeline Orchestration

The orchestrateEventExecution() method in accounting.service.ts runs the complete double-entry pipeline entirely on the client side:

  1. POST /transactions → Create Accounting Transaction
  2. POST /journal-entries → Create Journal Entry
  3. POST /journal-entry-lines × 2 → Debit + Credit lines
  4. POST /ledger-entries → Create Ledger Entries
🚨
Critical financial integrity risk. If the user loses internet after step 2 but before step 4, the ledger is in an inconsistent state — journal exists with no ledger posting. This must be a server-side atomic transaction: one POST /events/{id}/post endpoint with a single DB transaction and rollback on failure.
⚠
High Risk: Duplicate Service Names

Two classes both named AccountingService:

  • projects/accounting/src/app/services/accounting.service.ts — event/transaction orchestration
  • projects/accounting/src/app/core/services/accounting.service.ts — report generation

Rename the core service to FinancialReportService.

⚠
High Risk: 8-Way Token Resolution in Auth Interceptor

Auth interceptor checks 8 different storage keys (Token, token, accessToken × 2 in both sessionStorage and localStorage). Sign of accumulated tech debt from multiple auth implementations. Use one canonical key and one storage location.

ℹ
Observation: API fetches size=1000 for all report data

Report service fetches ?page=1&size=1000 for transactions, journal entries, lines, and ledger entries. At scale this causes very slow loads, browser memory pressure, and API timeouts. Reports should be generated server-side as pre-computed results, not raw data for client-side aggregation.

Nigerian Market Compliance Notes

  • FIRS Requirements: Tax Summary must support VAT (7.5%), WHT (varying rates by payment type), and CIT (30%). Tax codes must be configurable and mapped to accounts.
  • CBN Maker-Checker: CBN guidelines require two-person authorisation on financial transactions above threshold. Current single-level approve is insufficient for regulated entities.
  • PENCOM (Pension): HR-sourced payroll journals must separately identify pension deductions — employee 8% + employer 10% — into dedicated pension liability accounts.
  • IFRS Adoption: Nigerian listed companies use IFRS. P&L must show Gross Profit (requires COST_OF_SALES type) and EBITDA to be IFRS-compliant.
  • Functional Currency: Base currency must be explicitly set (NGN). Multi-currency transactions require FIRS-approved exchange rates (CBN rate preferred for tax purposes).
ℹ
Summary: OptimaXERP's Accounting module has a solid foundation — the double-entry mechanics, COA structure, journal entry pipeline, and report API architecture are architecturally sound. The critical work is in three areas: (1) moving the posting pipeline to the server, (2) adding missing sub-modules (AR, AP, Tax, Fixed Assets, Period Close, and full Payment Runs consolidation across all modules), and (3) standardising terminology. A professional financial controller should be able to use this module with minimal training after these changes.
